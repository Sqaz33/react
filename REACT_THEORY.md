Последнее обновление: **2026-09-23**

Этот файл повторяет теорию в порядке наших уроков. Отметка «пройдено» означает,

## 0. Проект и запуск — пройдено

- React-приложение находится в `D:\react\react`.
- Команды npm выполняются там, где лежит `package.json`.
- `npm run dev` запускает сервер разработки.
- `npm run lint` проверяет код, `npm run build` собирает production-версию.
- `main.jsx` создаёт корень React и подключает глобальный `index.css`.
- `App.jsx` — корневой компонент текущего интерфейса.

## 1. React, React DOM и рендер — пройдено

- `react` даёт компоненты, JSX-модель, state и хуки.
- `react-dom` связывает React с браузерным DOM.
- `createRoot(...).render(<App />)` запускает первоначальный рендер.
- Рендер — вычисление того, как должен выглядеть интерфейс сейчас.
- Commit — применение необходимых изменений к настоящему DOM.
- После изменения state React может заново вызвать компоненты, но React DOM
  изменяет только отличающиеся части страницы, а не пересоздаёт весь документ.

## 2. Функциональные компоненты — пройдено

Компонент — функция с именем с заглавной буквы, возвращающая JSX:

```jsx
function TodoHeader() {
  return <h1>Todo</h1>
}
```

- Пользовательский компонент используется как `<TodoHeader />`.
- `export default` экспортирует компонент, `import` подключает его в другом
  модуле.
- Компонент должен возвращать один корневой JSX-элемент или фрагмент.

## 3. JSX — пройдено

- JSX похож на HTML, но является синтаксисом JavaScript.
- JavaScript-выражение вставляется через `{...}`.
- Атрибут класса называется `className`, обработчики — `onClick`, `onChange`.
- Имена многих DOM-свойств записываются в camelCase.
- Все теги закрываются, включая `<input />`.
- Несколько соседних элементов можно обернуть во фрагмент `<>...</>`.
- `true`, `false`, `null` и `undefined` сами по себе ничего не рисуют.
- В обработчик передают функцию, а не результат её немедленного вызова.

## 4. Props — пройдено

Props — входные данные компонента от родителя:

```jsx
function TodoHeader({total}) {
  return <span>Всего: {total}</span>
}
```

- Props доступны только для чтения: ребёнок не должен их изменять.
- Деструктуризация `{total}` достаёт свойство из объекта props.
- Изменение props родителем приводит к новому рендеру ребёнка.

## 5. Списки, `map` и `key` — пройдено

- `map` вызывает callback для каждого элемента и создаёт новый массив той же
  длины.
- В React `map` часто превращает массив данных в массив JSX-элементов.
- У элементов списка нужен стабильный `key`, обычно идентификатор записи.
- `key` помогает React сопоставлять старые и новые элементы списка.
- `key` — специальный атрибут React: он не попадает в props компонента.

## 6. State и `useState` — пройдено

```js
const [title, setTitle] = useState('')
```

- `title` — снимок состояния для текущего рендера.
- `setTitle` просит React сохранить новое значение и запланировать рендер.
- Изменять state напрямую нельзя: React узнаёт об обновлении через setter.
- Если новое значение зависит от предыдущего, используется функциональная
  форма: `setValue(current => nextValue)`.

## 7. События, формы и controlled input — пройдено

- Обработчик получает объект события: `onChange={event => ...}`.
- `event.preventDefault()` отменяет стандартную отправку формы.
- `type="submit"` отправляет форму, `type="button"` выполняет обычное действие.
- Controlled input получает `value` из state и обновляет его в `onChange`.
- Checkbox управляется свойством `checked`, а не `value`.

Поток controlled input:

```text
ввод → onChange → setter → рендер → новое value/checked
```

## 8. Подъём состояния и callback-props — пройдено

- Общее состояние хранится у ближайшего общего родителя.
- Родитель передаёт данные вниз через props.
- Ребёнок сообщает о событии вверх через переданную функцию-callback.

Поток Todo:

```text
TodoItem → callback → App → setTodos → рендер → новые props
```

Промежуточный `TodoList` может только передавать callback дальше. Такая цепочка
называется prop drilling; для небольшого дерева она нормальна.

## 9. Иммутабельные обновления — пройдено

State нельзя менять методами `push`, `splice` или мутирующим `sort`.

- Добавление: создать новый массив через spread.
- Переключение: `map` возвращает новый массив, а изменяемая задача копируется
  через object spread.
- Удаление: `filter` возвращает массив без задачи с выбранным `id`.

Функциональный setter даёт актуальное предыдущее состояние, но не разрешает его
мутировать. Нужно вернуть новое значение с новой ссылкой.

## 10. Один источник истины — пройдено

- `completed` хранится только в массиве `todos` внутри `App`.
- `TodoItem` не создаёт вторую копию `completed` в локальном state.
- Checkbox читает `item.completed` и сообщает родителю только `item.id`.
- Дублирование одного значения в нескольких state приводит к рассинхронизации.

## 11. Минимальное состояние и вычисляемые значения — пройдено

- В state хранится только то, что нельзя полностью вычислить из других state
  или props.
- `total = todos.length` и количество невыполненных вычисляются при рендере.
- Для простых вычислений не нужны отдельные state, Effect или `useMemo`.
- После изменения `todos` компонент вызывается снова, поэтому производные
  значения автоматически пересчитываются.
- Во Vue ближайшая аналогия — `computed`, но в React часто достаточно обычной
  переменной в теле компонента.

## 12. Условный рендеринг — пройдено

- Ранний `return` удобен, когда компонент должен вернуть полностью другой JSX.
- Тернарный оператор выбирает один из двух вариантов:
  `condition ? trueJSX : falseJSX`.
- `condition && jsx` показывает элемент только при истинном условии.
- С числом нужно писать `items.length > 0 && ...`, иначе React может вывести
  `0`.
- Пустота списка вычисляется через `todos.length`, отдельный `isEmpty` state не
  нужен.

## 13. Композиция и `children` — пройдено

- JSX между открывающим и закрывающим тегами компонента попадает в специальный
  prop `children`.
- Компонент-оболочка определяет структуру, а родитель определяет содержимое.
- `children` подходит для layout, panel, card и modal.
- Данные с конкретным смыслом (`total`, `todos`) остаются обычными props.
- Во Vue ближайшая аналогия — default slot.

## 14. Чистота рендера — пройдено

Компонент во время рендера должен вести себя как чистая функция от props, state
и context:

- одинаковые входы должны давать одинаковый JSX;
- нельзя мутировать props, state и существующие внешние объекты;
- нельзя вызывать setters прямо во время рендера;
- нельзя во время рендера выполнять `fetch`, менять DOM, запускать таймеры или
  записывать в `localStorage`;
- разрешено читать данные, создавать новые локальные значения, использовать
  чистые `map`/`filter` и объявлять обработчики событий.

`onClick={() => setValue(...)}` только создаёт обработчик; setter выполнится
после клика. `onClick={setValue(...)}` вызывает setter немедленно при рендере и
может создать бесконечный цикл.

React может повторять или отменять render phase, а `StrictMode` в разработке
помогает замечать нечистую логику. Побочные эффекты выполняются в обработчиках
событий или, когда нужна синхронизация с внешней системой, в `useEffect`, который
будет изучен позже.

Проверка пройдена: чистыми распознаны вычисление производного значения через
`filter` и создание функции-обработчика. Мутация state через `push`, немедленный
вызов setter в JSX и запись в `localStorage` правильно распознаны как
недопустимые во время рендера.

## 15. CSS, встреченный в проекте

- Глобальный CSS подключён в `main.jsx` через `import './index.css'`.
- В JSX пишется `className="todo-item"`, в CSS — `.todo-item`.
- Несколько классов в JSX разделяются пробелом:
  `className="todo-item completed"`.
- `.todo-item.completed` означает один элемент с двумя классами.
- `.todo-item .todo-title` означает потомка внутри `.todo-item`.
- `display: flex` располагает дочерние элементы по основной оси; `gap` задаёт
  промежутки, `align-items` выравнивает по поперечной оси.
- `margin-left: auto` забирает свободное место перед flex-элементом и прижимает
  его вправо; порядок DOM при этом не меняется.
- `max-width` ограничивает ширину, а `margin: ... auto` центрирует блок.
- У `<ul>` есть браузерные `margin`, `padding` и маркеры; их можно сбросить.
- CSS не может выбрать отдельный текстовый узел, поэтому название задачи
  обёрнуто в `.todo-title` для отдельного зачёркивания.

## 17. Устройство Vite-проекта — пройдено

Цепочка запуска:

```text
npm → package.json scripts → Vite → index.html → main.jsx → App → компоненты
```

- `package.json` описывает проект, npm-скрипты и зависимости.
- `package-lock.json` фиксирует точные версии всего дерева npm-зависимостей;
  обычно он обновляется npm и коммитится вместе с `package.json`.
- `node_modules` содержит установленные пакеты, генерируется через npm и не
  коммитится.
- `index.html` — HTML-оболочка с `<div id="root">` и подключением `main.jsx`.
- `src/main.jsx` — точка входа JavaScript: подключает CSS и `App`, создаёт React-
  корень и запускает первоначальный рендер.
- `src/App.jsx` — обычный, а не магический компонент; корневым он становится,
  потому что `main.jsx` передаёт `<App />` в `render`.
- `src` содержит исходный код и импортируемые ресурсы, которые обрабатывает
  Vite.
- `public` содержит статические файлы, доступные от корня сайта без импорта и
  без преобразования сборщиком, например `/favicon.svg`.
- `vite.config.js` настраивает Vite; React-плагин обрабатывает React/JSX.
- `dist` — сгенерированный результат `npm run build`; его не редактируют вручную
  и в этом проекте не коммитят.
- `.gitignore` перечисляет генерируемые и локальные файлы, которые Git должен
  игнорировать, включая `node_modules` и `dist`.

Браузер не выполняет JSX напрямую. В режиме разработки Vite принимает запрос к
`/src/main.jsx`, преобразует JSX через React-плагин и отдаёт браузеру обычный
JavaScript-модуль. При `npm run build` Vite заранее преобразует и собирает код в
файлы внутри `dist`; браузер в production также получает JavaScript, а не JSX.

Обычная клиентская сборка Vite создаёт статические файлы `index.html`, CSS и
JavaScript. Код используемых `react` и `react-dom` включается в JavaScript-бандл
(возможны несколько файлов при разделении кода), минифицируется и загружается
браузером. Это не означает, что весь интерфейс заранее превращён в HTML:
`index.html` по-прежнему содержит корневой контейнер, а React DOM после загрузки
JavaScript создаёт и обновляет DOM на клиенте. Предварительный HTML требует
отдельного SSR или static generation, которых в текущем проекте нет.

## 18. Базовый цикл Git — пройдено

Git хранит три основных состояния:

```text
рабочая папка → staging area (index) → история коммитов
              git add              git commit
```

- Рабочая папка содержит текущие файлы и незакоммиченные изменения.
- Staging area содержит выбранную версию файлов для следующего коммита.
- Коммит — сохранённый снимок только staged-изменений с сообщением и автором.
- `git status` показывает изменённые, staged и untracked-файлы.
- `git diff` показывает unstaged-изменения относительно staging area.
- `git add <path>` помещает текущую версию выбранного файла в staging area; он
  не создаёт коммит и не отправляет код в интернет.
- `git diff --staged` показывает, что именно войдёт в следующий коммит.
- `git commit -m "сообщение"` создаёт локальный коммит из staged-изменений.
- `git log --oneline` показывает краткую историю коммитов.
- Коммит остаётся локальным; отправка в удалённый репозиторий выполняется
  отдельной командой `git push`, которая в этот урок не входит.

В diff строки с `-` удалены, строки с `+` добавлены, а строки без такого
префикса показаны для контекста. Лучше добавлять конкретные файлы, а не слепо
использовать `git add .`, если в рабочей папке есть несвязанные изменения.

Пользователь уже владел базовыми командами. Новыми вариантами стали
`git diff --staged` для просмотра будущего коммита и
`git diff -- path/to/file` для просмотра выбранного файла.

## 19. `find`, `some`, `every` — пройдено

Все три метода принимают callback с условием и не изменяют исходный массив:

- `find` возвращает первый подходящий элемент или `undefined`;
- `some` возвращает `true`, если подходит хотя бы один элемент;
- `every` возвращает `true`, если подходят все элементы.

Методы прекращают перебор, когда результат уже известен. Для пустого массива
`some` возвращает `false`, а `every` — `true`: нет ни одного элемента,
нарушающего условие. Перед использованием результата `find` нужно учитывать
возможный `undefined`.

Практика в Todo: `find` определяет следующую невыполненную задачу, `some`
показывает наличие хотя бы одной выполненной, а `every` — состояние «выполнены
все». Все три значения вычисляются из `todos` во время рендера без нового state.

Для пользовательского состояния «все задачи выполнены» перед `every` нужна
проверка `todos.length > 0`, иначе пустой массив даст `true`. Boolean-значения
получили говорящие имена `hasCompletedTodos` и `areAllTodosCompleted`, а результат
`find` проверяется перед чтением данных найденной задачи.

## 20. `reduce` — пройдено

`reduce` последовательно сворачивает массив в одно итоговое значение. Итогом
может быть число, строка, объект или массив.

```js
const result = items.reduce((accumulator, currentItem) => {
  return nextAccumulator
}, initialValue)
```

- `accumulator` хранит результат предыдущего шага;
- `currentItem` — текущий элемент массива;
- `initialValue` становится аккумулятором перед первым элементом;
- значение, возвращённое callback, становится аккумулятором следующего шага;
- после последнего элемента `reduce` возвращает финальный аккумулятор.

Начальное значение лучше передавать явно: с ним понятен тип аккумулятора, а
пустой массив возвращает это значение. Без начального значения пустой массив
вызывает ошибку. Частая ошибка — забыть `return`, после чего на следующем шаге
аккумулятор станет `undefined`.

`reduce` не заменяет остальные методы: для преобразования обычно яснее `map`,
для отбора — `filter`, для поиска — `find`, для boolean-проверок — `some` или
`every`. Он нужен, когда из набора элементов собирается одно итоговое значение.

Практика в Todo: `completedCount` вычисляется с аккумулятором-числом и начальным
значением `0`. Явное условие возвращает `sum + 1` для выполненной задачи и
неизменённый `sum` для невыполненной. Сложение числа с boolean технически
работает через преобразование `true`/`false` в `1`/`0`, но явное условие понятнее.

## 21. `sort` — пройдено

`.sort(compareFunction)` упорядочивает элементы и возвращает ссылку на тот же
массив. Без функции сравнения значения приводятся к строкам и сравниваются как
текст, поэтому числовой порядок может оказаться неожиданным.

Функция сравнения получает два элемента `a` и `b`:

- отрицательное число — `a` должно стоять раньше `b`;
- положительное число — `b` должно стоять раньше `a`;
- `0` — их относительный порядок менять не нужно.

Для чисел по возрастанию используется `a - b`, по убыванию — `b - a`. Для строк
подходит `a.localeCompare(b)`.

Обычный `.sort()` мутирует массив. Поэтому нельзя вызывать `todos.sort(...)` на
массиве из React-state. Сначала создаётся новый массив через `[...todos]`, и уже
его можно сортировать. Сортировка для отображения является вычисляемым значением:
ей не нужны отдельный state, setter или Effect. Современный `toSorted()` сразу
возвращает копию, но в первой практике используется копирование плюс `.sort()`,
чтобы явно закрепить мутацию этого метода.

Хорошая функция сравнения чистая и предсказуемая: не меняет элементы, не вызывает
setter и для одной пары всегда возвращает одинаковый результат. Для равных по
критерию элементов нужно возвращать `0`; современная стабильная сортировка тогда
сохраняет их исходный относительный порядок. Возвращать именно `-1` и `1` не
обязательно — важен знак числа. Поля с известным типом сравниваются строго через
`===`.

Практика в Todo: `[...todos]` создаёт копию state, а comparator
`Number(a.completed) - Number(b.completed)` помещает `false` (`0`) раньше
`true` (`1`). При одинаковых значениях разность равна нулю, поэтому относительный
порядок задач одной группы сохраняется. В `TodoList` передаётся `sortedTodos`, а
исходный `todos` остаётся источником данных для остальных вычислений.

## 22. Объекты, spread/rest и деструктуризация — пройдено

Объект хранит связанные именованные свойства. Запись `const copy = original`
копирует только ссылку: обе переменные указывают на один объект. Object spread
в выражении объекта создаёт новый внешний объект:

```js
const updated = { ...todo, completed: true }
```

Свойства применяются слева направо, поэтому более позднее `completed` заменяет
скопированное. Обратный порядок `{ completed: true, ...todo }` восстановил бы
старое значение из `todo`.

Деструктуризация извлекает свойства в переменные:

```js
const { title, completed } = todo
```

Object rest находится слева при разборе объекта и собирает оставшиеся свойства:

```js
const { title, ...todoData } = todo
```

В `{ ...todoData, title }` тот же синтаксис уже является spread: он раскрывает
свойства в новый объект. Короткая запись `title` равна `title: title`.

Spread выполняет поверхностное копирование. Внешний объект становится новым, но
вложенный объект сохраняет старую ссылку. Для изменения вложенного уровня нужно
копировать каждый изменяемый уровень отдельно. В React это важно для
иммутабельного обновления state; props также нельзя изменять.

Практика в Todo: копия задачи создаётся через spread исходного объекта, после
чего более поздние `id`, `title` и `completed` заменяют старые значения. В
`TodoList` деструктуризация `{ todos, ...itemProps }` отделяет список, а rest
собирает остальные callback-props; JSX spread передаёт их в каждый `TodoItem`.
Rest не является обязательным при простой перезаписи свойств — в таком случае
прямой `{ ...original, changed: value }` часто понятнее.

## 23. Ссылочное равенство и мутация — пройдено

Примитивы сравниваются по значению, а объекты и массивы — по ссылке. Два отдельно
созданных одинаковых объекта не равны через `===`; две переменные равны, если
указывают на один объект. `const` запрещает переназначить переменную, но не
запрещает менять свойства объекта или элементы массива.

Мутация изменяет существующий объект. Для React-state это нарушает модель
снимков: старые рендеры и другие ссылки начинают видеть изменённые данные, а
передача setter той же ссылки может не запланировать ожидаемое обновление.

Spread копирует только один уровень:

```js
const nextTodos = [...todos]
```

Массив новый, но `nextTodos[0] === todos[0]`. Аналогично `{ ...todo }` создаёт
новую задачу, но вложенное `details` остаётся той же ссылкой. При изменении
`details.priority` иммутабельное обновление должно создать новые ссылки на массив,
изменяемую задачу и `details`; неизменённые задачи полезно вернуть как есть.

React сравнивает старое и новое значение state через семантику `Object.is`.
Новая ссылка сообщает, что контейнер изменился, но сама по себе не делает
вложенные данные независимыми. Копировать нужно каждый изменяемый уровень, а не
всё дерево без разбора.

Практика в Todo: при переключении `details.priority` через `map` создаются новый
массив, новая выбранная задача и новый `details`; другие задачи возвращаются как
есть. Неизменённые вложенные объекты также могут сохранять старые ссылки — это
структурное разделение, а не ошибка. Новая задача сразу получает полную ожидаемую
форму с `details`, иначе JavaScript-сборка не заметила бы отсутствующее поле, а
ошибка проявилась бы только при чтении в браузере.

Полное копирование и обновление существующего state имеют разные цели. При
обновлении копируется путь к изменяемому значению. При создании отдельного
дубликата сущности допустим `structuredClone`, если требуется независимость всех
поддерживаемых вложенных данных; это осознанное решение, а не обязательный шаблон
для каждого обновления.

## 24. Scope, closures и callbacks — пройдено

Scope определяет, где доступно имя. `let` и `const` имеют блочную область
видимости, параметры и локальные переменные функции доступны только внутри неё,
а вложенная функция может читать имена из внешней лексической области.

Callback — функция, переданная другому коду для последующего вызова. В Todo
callback вызывают методы массивов, React setter и система событий. Передача
`onClick={handler}` передаёт функцию, а `onClick={handler()}` вызывает её во время
рендера и передаёт результат.

Closure (замыкание) возникает, когда функция сохраняет доступ к лексическому
окружению места создания. В обычном JavaScript замыкаются привязки переменных. В
React каждый рендер создаёт новый набор локальных значений и обработчиков, поэтому
обработчик конкретного рендера видит props/state этого рендера — его снимок.

В `onClick={() => onToggleTodo(item.id)}` стрелочная функция замыкает `item.id` и
`onToggleTodo`. В `currentTodos => ...` React сам передаёт актуальный предыдущий
state аргументом. Если новое состояние зависит от текущего, setter-callback
предпочтительнее чтения `todos` из замыкания.

Updater-функция должна быть чистой: React в Strict Mode может вызвать её повторно
для проверки. Поэтому получение времени, случайного значения и другие нечистые
действия выполняются в обработчике события до setter, а готовое значение можно
замкнуть и использовать внутри updater.

Практика в Todo: `duplicateTodo(id)` создаёт `newId` в обработчике, затем передаёт
React чистый updater. React вызывает его с актуальным `curTodos`; updater замыкает
`id` и `newId`. Вложенный callback `find` отдельно получает текущий `todo` от
самого метода массива. Если задача не найдена, возвращается прежний массив; если
найдена — новый массив с дубликатом.

## 25. ES-модули — пройдено

Каждый файл с `import`/`export` является модулем и имеет собственную область
видимости: его локальные имена не становятся глобальными. Экспорт делает выбранное
значение доступным другим модулям, а импорт создаёт доступ к экспортированной
привязке.

Named exports позволяют экспортировать несколько значений и импортируются в
фигурных скобках под точными именами. Их можно переименовать через `as`. Default
export в модуле может быть только один и импортируется без фигурных скобок; имя
при импорте выбирает получатель. Текущие React-компоненты используют default
export, но компоненты не требуют его — это обычное соглашение проекта.

Статические `import` располагаются на верхнем уровне. Vite строит по ним граф
зависимостей, преобразует JSX и собирает production-файлы. Код верхнего уровня
модуля выполняется один раз при загрузке модуля, после чего его exports
переиспользуются. Импортированные привязки нельзя переназначать.

Циклических зависимостей (`a` импортирует `b`, а `b` импортирует `a`) лучше
избегать. Чистые константы и функции предметной логики удобно хранить в обычном
`.js`-модуле, который ничего не знает о React-компонентах.

Практика в Todo: модуль `priority.js` предоставляет named exports
`PRIORITY_LABELS` и `getNextPriority`. `TodoItem` импортирует данные для
отображения, а `App` — чистую функцию предметной логики. Компоненты не импортируются
обратно в utility-модуль, поэтому граф зависимостей направлен в одну сторону и не
содержит цикла.

## 26. Promise, async/await и try/catch/finally — пройдено

Promise представляет будущий результат асинхронной операции. Он создаётся в
состоянии `pending`, затем один раз переходит в `fulfilled` со значением или в
`rejected` с причиной ошибки. После этого Promise считается settled и повторно
изменить его результат нельзя.

`.then` обрабатывает успешное значение, `.catch` — отклонение, `.finally`
выполняется после любого исхода и не получает результат операции. Каждый вызов
возвращает новый Promise, поэтому обработчики образуют цепочку; возвращённое
значение становится результатом следующего шага, а `throw` переводит цепочку в
rejected.

Функция с `async` всегда возвращает Promise. `await` можно использовать внутри
`async`: он ждёт settlement, возвращает fulfilled-значение или выбрасывает
rejection как исключение. `await` приостанавливает только текущую async-функцию,
а не блокирует браузер.

`try` содержит ожидаемую операцию и success-логику, `catch` получает ошибку, а
`finally` подходит для обязательной очистки — например, снятия `isSaving` при
успехе и ошибке. Async-действие, вызванное кликом, остаётся в обработчике события;
для него не требуется `useEffect`.

Практика в Todo: `saveTodos` создаёт Promise и вызывает `resolve`/`reject` внутри
callback `setTimeout`, поэтому задержка действительно определяет settlement.
Пустая функция таймера сама по себе не является ожиданием: `setTimeout` лишь
регистрирует callback и немедленно возвращает идентификатор.

`handleSaveTodos` включает loading, очищает старое сообщение и ожидает сервис.
Успешное значение обрабатывается в `try`, `Error` — в `catch`, а `finally`
снимает loading при любом исходе. Во время pending кнопка disabled и показывает
`Сохранение...`; HTTP и Effect для действия по клику не нужны.

## 27. Event loop — пройдено

Синхронный JavaScript выполняется в call stack до его освобождения. Таймеры и
события обслуживает окружение браузера; готовые callback-функции попадают в
очередь tasks. Продолжение после `await` и обработчики Promise попадают в очередь
microtasks.

После завершения текущей task движок выполняет все накопившиеся microtasks, затем
браузер получает возможность отрисовать изменения и берётся следующая task.
`setTimeout(callback, 0)` означает «не раньше указанной задержки», а не
«выполнить немедленно». `await` приостанавливает только текущую async-функцию и
не блокирует интерфейс.

Проверочный порядок для синхронных `console.log`, `Promise.resolve().then(...)`
и `setTimeout(..., 0)` определён верно: сначала выполняется весь синхронный код,
потом microtask Promise и только затем task таймера. В текущем fake-save callback
таймера вызывает `resolve` или `reject`, что ставит продолжение после `await` в
очередь microtasks.

## 28. Debounce на поиске — пройдено

Debounce откладывает вызов функции до тех пор, пока события не прекратятся на
заданное время. Каждый новый вызов отменяет предыдущий таймер и создаёт новый.
Поэтому серия быстрых вводов приводит к одному итоговому запуску после паузы.

Простой `setTimeout` на каждое событие не является debounce: без
`clearTimeout` выполнятся все созданные callbacks. Debounce использует замыкание,
чтобы помнить идентификатор предыдущего таймера между вызовами. В поиске обычно
разделяются немедленное значение поля и отложенное значение, по которому
запускается дорогая фильтрация или сетевой запрос.

В React поле должно оставаться отзывчивым: `searchText` обновляется при каждом
вводе, а отдельное отложенное значение меняется только после паузы. Effect при
изменении `searchText` создаёт новый таймер; его cleanup вызывает `clearTimeout`
перед следующим effect и тем самым отменяет устаревшее обновление.

Практика в Todo: controlled-компонент `TodoSearch` передаёт мгновенную строку в
`App`, а `visibleTodos` фильтруется по значению, обновляемому через 400 мс после
последнего ввода. Сортировка сохраняется, статистика продолжает вычисляться по
полному массиву задач.

## 29. Правила хуков — пройдено

React связывает внутренние ячейки состояния с порядком вызовов hooks во время
рендера. Поэтому hooks вызываются только на верхнем уровне компонента или
собственного hook: не внутри условий, циклов, вложенных функций и не после
условного раннего возврата.

Hooks вызываются только из React-компонентов и собственных hooks. Обычная
JavaScript-функция не должна вызывать `useState` или `useEffect`. Имя собственного
hook начинается с `use`, а имя компонента — с заглавной буквы. Вызов setter в
обработчике разрешён: setter не является hook, hook был вызван при рендере.

Custom hook — обычная JavaScript-функция с именем, начинающимся на `use`. Она
выполняется во время рендера вызывающего компонента, может принимать аргументы и
возвращать значения. Особого синтаксиса нет; специальны правила вызова и
возможность использовать внутри другие hooks. Каждый вызов получает независимое
состояние React и переиспользует логику, а не один общий state.

Практика в Todo: `useDebouncedValue(value, delay)` содержит `useState` и
`useEffect`, возвращает отложенное значение и вызывается безусловно в начале
`App`. После его появления debounce-логика исчезла из компонента, а поведение
поиска осталось прежним.

## 30. `useEffect` и внешняя синхронизация — пройдено

Рендер должен оставаться чистым: по props и state он вычисляет JSX и не изменяет
внешний мир. `useEffect` нужен, когда после commit требуется синхронизировать
компонент с системой вне React: браузерным API, таймером, подпиской, соединением
или сторонним виджетом.

Effect состоит из setup и необязательного cleanup. При изменении зависимости
React сначала выполняет cleanup предыдущего effect со значениями предыдущего
рендера, затем запускает новый setup. При удалении компонента выполняется
последний cleanup. В режиме разработки Strict Mode React дополнительно проверяет
симметрию последовательностью setup → cleanup → setup.

Все реактивные значения, прочитанные setup или cleanup, должны находиться в
dependency array. React сравнивает каждую зависимость с прошлой через
`Object.is`. Без массива effect запускается после каждого commit, с `[]` — после
первого commit, а с `[a, b]` — также после изменения `a` или `b`.

`navigator.onLine` является обычным снимком браузерного состояния и сам не
запускает React-рендер. State служит реактивным мостом: браузерное событие
вызывает setter, React рендерит компонент и custom hook возвращает новое значение.
Возврат из setup — инструкция cleanup для React, а возврат из custom hook — его
обычный результат для вызывающего компонента.

Практика в Todo: `useOnlineStatus` постоянно слушает оба события `online` и
`offline`, меняет state соответствующими обработчиками и удаляет обе подписки в
cleanup. Подписка существует всё время жизни компонента, поэтому effect имеет
пустой dependency array. Статус передаётся в `TodoHeader` и выводится через
`dd` с `role="status"`.

## 31. События и Effects — пройдено

Обработчик события запускается потому, что произошло конкретное взаимодействие:
клик, submit или изменение поля. Effect запускается потому, что компонент
отображается и должен оставаться синхронизированным с внешней системой при
изменении зависимостей. Асинхронность сама по себе не определяет выбор.

Действие пользователя не следует превращать в state-флаг, за которым наблюдает
Effect: обработчик уже знает точную причину и должен выполнить действие напрямую.
Effect, наоборот, не вызывается вручную — React управляет его setup и cleanup в
соответствии с жизнью компонента и dependency array.

Асинхронность не определяет выбор: запрос сохранения по кнопке относится к
обработчику, а подписка на внешний источник во время присутствия компонента — к
Effect. Корректные зависимости и cleanup предотвращают накопление таймеров и
подписок, но не являются причиной переносить пользовательское действие в Effect.

Практика в Todo: кнопка «Удалить выполненные» напрямую вызывает переданный из
`App` обработчик. Он через функциональный setter и `filter` оставляет только
незавершённые задачи; отдельные state-флаг и Effect не создаются.

## 32. `localStorage` без лишних Effects — пройдено

`localStorage` — синхронное браузерное хранилище строк, привязанное к origin.
`getItem(key)` возвращает строку или `null`, а `setItem(key, value)` сохраняет
строку. Объекты и массивы требуют явных `JSON.stringify` и `JSON.parse`.

Начальное чтение state не следует выполнять Effect после первого рендера: это
сначала покажет fallback, затем вызовет второй рендер. Lazy initializer
`useState` читает сохранённое значение только при создании состояния. Запись при
изменении `todos` является настоящей синхронизацией React-state с внешней
системой и может выполняться одним Effect.

Lazy initializer передаётся как функция без вызова: `useState(load)`. В отличие
от него Effect с `[]` выполняется лишь после первого commit, поэтому загрузка
через setter дала бы сначала пустой интерфейс и второй рендер. Effect без массива
выполнялся бы после каждого commit и мог создать цикл обновлений.

Практика в Todo: `storage.js` содержит fallback, чтение, проверку массива и
запись JSON. `App` получает начальный `todos` через lazy initializer, а Effect с
зависимостью `[todos]` сохраняет любые последующие изменения. При отсутствии
ключа loader возвращает начальные задачи, которые Effect затем записывает в
хранилище; имена ключей регистрозависимы.

## 33. `useRef` и DOM — пройдено

`useRef(initialValue)` возвращает один стабильный объект `{ current }`, который
сохраняется между рендерами. В отличие от state, изменение `.current` не просит
React выполнить новый рендер. Поэтому ref подходит для данных, которые нужно
помнить, но которые сами по себе не отображаются в JSX.

При передаче ref DOM-элементу через атрибут `ref` React после commit записывает в
`.current` реальный узел браузера, а при удалении узла устанавливает `null`.
DOM-ref используют из обработчика или Effect, а не читают как источник данных
для JSX во время рендера.

Ref не заменяет controlled state: state хранит отображаемое значение и вызывает
рендер, а ref предоставляет императивный доступ к DOM без рендера. Ref следует
размещать у ближайшего компонента, которому действительно нужен узел; поднимать
его в родителя без внешнего управления не требуется.

Практика в Todo: `TodoForm` хранит `title` в state и локальный `inputRef` отдельно.
После успешного submit задача добавляется, state очищается, а вызов
`inputRef.current?.focus()` возвращает курсор в существующий input без Effect.

## 34. Собственный hook `useLocalStorage` — пройдено

Custom hook позволяет объединить React-state и его синхронизацию с внешней
системой за одним переиспользуемым интерфейсом. `useLocalStorage` принимает ключ
и начальное значение, а возвращает пару `[value, setValue]`, чтобы вызывающий код
использовал обычное и функциональное обновление так же, как с `useState`.

Первое чтение выполняется lazy initializer внутреннего `useState`; Effect
сохраняет сериализованное значение при изменении `key` или `value`. Hook не должен
знать названия `todos` или структуру конкретного приложения: предметные данные и
ключ передаются аргументами.

Низкоуровневые операции можно оставить в отдельном `storage.js`: этот модуль
работает с ключом, fallback и сериализуемым значением, а custom hook добавляет
React-state и Effect. Такое разделение сохраняет универсальность и не смешивает
браузерный API с предметной моделью Todo.

Практика в Todo: `App` вызывает `useLocalStorage(TODO_KEY, initialTodos)` и
получает `[todos, setTodos]`. Lazy initializer делегирует чтение `storage.load`,
Effect делегирует запись `storage.save`, а возвращённый setter поддерживает все
существующие функциональные обновления.

Рендер компонента планируется при обновлении его state, при рендере родителя с
его дочерним элементом или при изменении читаемого context/внешнего store. При
локальном state React отмечает соответствующий Fiber и путь до корня; в
прикладной модели повторно вычисляются компонент-владелец state и его потомки,
а несвязанные предки и соседние ветки не вызываются заново. React может
пропустить потомка через bailout, например при `memo` и неизменных props.

Собственный hook не создаёт узел дерева: его state принадлежит компоненту,
который вызвал hook. Поэтому setter внутри `useDebouncedValue`, вызванного из
`App`, планирует рендер `App`. Render повторно вызывает функции компонентов и
строит новое описание UI; commit применяет только реальные различия к DOM.

## 35. `useReducer` — пройдено

`useReducer` — второй способ хранить state компонента. Он полезен, когда одно
состояние имеет несколько связанных переходов и многочисленные обработчики
должны изменять его по единым правилам. Это не обязательная замена `useState`:
для простого независимого значения `useState` обычно понятнее.

Вызов `useReducer(reducer, initialState)` возвращает `[state, dispatch]`.
`dispatch(action)` сообщает, что произошло. React передаёт прежний state и action
в reducer, получает новый state и планирует рендер. Action обычно является
объектом с полем `type` и, если нужны данные, полем `payload`.

Reducer — чистая функция `(state, action) => nextState`. Он не изменяет прежний
объект, не обращается к `localStorage` или сети, не запускает таймеры и не
генерирует случайные значения. Один и тот же state и action должны давать один
результат. Неизменившаяся ветка возвращает прежний state, изменившаяся — новый
объект или массив.

После `dispatch` переменная `state` в текущем обработчике остаётся снимком
текущего рендера; новое значение будет доступно на следующем рендере. Логика
перехода находится в reducer, а побочный эффект, например запрос сохранения,
остаётся в обработчике или подходящем Effect.

Первая практика в Todo: объединить связанные `isSaving` и `saveMessage` в
состояние `{ status, message }`. Действия `save/started`, `save/succeeded` и
`save/failed` описывают событие, а reducer определяет итоговый status и message.
Асинхронный вызов сервиса в reducer не переносится.

Чистая часть практики выполнена: `saveReducer` обрабатывает три action через
`switch`, создаёт новые объекты состояния и возвращает прежний state для
неизвестного типа. Следующий этап — вызвать `useReducer` в `App`; обработчик
сохранения будет отправлять actions до и после `await` вместо вызова двух
независимых setters.

Практика завершена: `App` вызывает `useReducer`, отправляет actions через
`dispatchSave`, а `saveReducer` централизованно переводит состояние между
`idle`, `saving`, `success` и `error`. Поле `action.type` описывает произошедшее
событие, тогда как `state.status` хранит текущий режим. В action передаются только
необходимые данные, потому что текущий state React сам передаёт reducer первым
аргументом.

Производные значения не дублируются: `isSaving` вычисляется сравнением status, а
сообщение читается из `saveState`. Компоненту `TodoHeader` передаются только
нужные ему props вместо всего внутреннего объекта reducer, что уменьшает связь
компонента со структурой состояния.

## 36. Context — пройдено

Context передаёт значение всем подходящим потомкам в React-дереве без ручной
пересылки одного и того же prop через каждый промежуточный компонент. Он полезен
для сквозных настроек: темы, локали, текущего пользователя или общего набора
настроек. Обычные предметные данные, нужные одному ближайшему ребёнку, обычно
лучше оставить явными props.

`createContext(defaultValue)` создаёт объект контекста и вызывается на уровне
модуля. `defaultValue` читается только тогда, когда над consumer нет подходящего
Provider; это статический fallback, а не state. В React 19 значение
предоставляется через `<SomeContext value={value}>`. В React 18 и старом коде
та же роль записывается как `<SomeContext.Provider value={value}>`.

Возвращённый объект нужно сохранить и экспортировать напрямую:
`const SomeContext = createContext(defaultValue)`. Нельзя оборачивать этот вызов
в функцию, создающую новый Context: Provider и `useContext` должны ссылаться на
один и тот же объект. Модуль создаёт его один раз при загрузке. В React 19 именно
этот специальный объект можно использовать и как JSX Provider, и как аргумент
`useContext`.

`useContext(SomeContext)` — hook, который вызывается на верхнем уровне
компонента. Он ищет ближайший Provider этого контекста выше по React-дереву. При
изменении предоставленного значения React рендерит компоненты, которые читают
этот Context. Значение от более далёкого Provider перекрывается ближайшим.

Context сам ничего не хранит и не обновляет. State остаётся у компонента-
владельца, а Provider распространяет его текущее значение. Context также не
является заменой всем props: чрезмерное использование скрывает зависимости
компонента и делает переиспользование сложнее.

Первая практика: `App` предоставляет поддереву тестовую строку темы.
`TodoLayout` читает тему через `useContext` и записывает её в `data-theme` у
`<main>`. Атрибут `data-*` является валидным HTML и позже послужит CSS-селектором;
на первом шаге внешний вид ещё не изменяется.

Статическая цепочка проверена: один объект `ThemeContext` импортируется в
Provider и consumer, поэтому `TodoLayout` получает строку без промежуточного
prop. Следующий шаг меняет контракт значения со строки на объект
`{ theme, toggleTheme }`: Context может передавать любое JavaScript-значение, но
Provider и все consumers должны одинаково понимать его форму.

Динамическое значение проверено: state живёт в `App`, функция изменения входит
в значение Provider, а два consumer обновляются после setter. Объект fallback с
пустой функцией может скрыть отсутствие Provider и ошибки его формы. Более
строгий вариант резервирует `null` как признак отсутствия Provider и предоставляет
custom hook `useTheme`: он вызывает `useContext`, выбрасывает понятную ошибку при
`null` и иначе возвращает согласованный объект темы.

Такой hook не создаёт новый Context и state; он централизует чтение и проверку
контракта. Его вызывают только компоненты ниже Provider. Компонент, который сам
возвращает Provider, не может прочитать этот Provider выше своего `return`:
`useContext` ищет Provider среди предков, а не среди JSX-потомков.

`aria-pressed` у toggle-кнопки не переключает стили и state. React только
записывает вычисленный boolean как доступное состояние кнопки; изменение темы
выполняет `onClick` и setter. Внешний вид можно отдельно связать с
`[aria-pressed="true"]` или, для всего layout, с `data-theme` в CSS.

Защитный вариант выполнен: consumers вызывают `useTheme`, а прямое использование
`useContext(ThemeContext)` осталось внутри одного custom hook. Provider по-
прежнему создаётся в `App`; Context распространяет объект, но не владеет state.

Для визуальной темы подходит CSS selector `.todo-layout[data-theme="dark"]`: без
пробела он выбирает один элемент, у которого одновременно есть класс и нужный
атрибут. CSS custom properties, объявленные на layout, наследуются потомками;
dark-selector может переопределить их, а существующие правила используют значения
через `var(--name)`.

Практика завершена: `App` хранит тему и предоставляет `{ theme, toggleTheme }`,
`TodoLayout` и `TodoHeader` читают её через защитный `useTheme`. Кнопка передаёт
действие обратно через функцию из Context, а CSS меняет фон, текст и границы по
`data-theme`. Context не заменяет state и не используется для Todo-данных, которым
достаточно существующих явных props.

## 37. `useMemo` и `useCallback` — пройдено

Оба hook сохраняют значение между рендерами, пока их зависимости не изменились,
но сохраняют разное. `useMemo(calculate, dependencies)` запоминает результат
вызова чистой функции `calculate`. `useCallback(callback, dependencies)`
запоминает саму ссылку на функцию и не вызывает её во время рендера.

На первом рендере React выполняет memo-calculation и сохраняет результат. На
следующих рендерах зависимости сравниваются через `Object.is`: если хотя бы одна
изменилась, вычисление выполняется заново; иначе возвращается прежний результат.
Все props, state и локальные реактивные значения, прочитанные callback, должны
быть перечислены в dependency array.

Memo-callback выполняется во время render phase, поэтому должен быть чистым: без
setter, запросов, DOM, таймеров и изменения исходных массивов. `useMemo` не делает
код асинхронным и не является гарантированным хранилищем данных; логика должна
оставаться правильной даже при повторном вычислении или сбросе кеша.

Эти hooks нужны только при конкретной причине: заметно дорогое вычисление,
передача стабильной ссылки memoized-компоненту или стабильность зависимости/
Context value. Простые производные значения следует продолжать вычислять обычными
переменными. В отличие от Vue `computed`, React `useMemo` требует ручного массива
зависимостей и рассматривается прежде всего как оптимизация.

Первая практика: учебно мемоизировать сортировку и фильтрацию `visibleTodos` по
`todos` и `debouncedSearchText`. Маленький текущий список не создаёт реальной
проблемы производительности; остальные счётчики намеренно остаются обычными
вычислениями.

Первый шаг выполнен: `visibleTodos` сохраняет вычисленный массив, пока не
изменились `todos` или отложенный запрос. Общая нормализация запроса находится
до перебора, а зависящее от каждого элемента название — внутри `filter`.

Следующий пример связывает оба hook. Обычная `toggleTheme` получает новую ссылку
при каждом рендере. `useCallback` может сохранить её, а `useMemo` — объект
`{ theme, toggleTheme }`. Если функция не стабилизирована, она сама будет
изменяющейся зависимостью и заставит memoized-объект создаваться заново.

Практика завершена: `toggleTheme` сохраняет ссылку через `useCallback`, потому
что использует только стабильный setter и функциональный updater. Объект Theme
Context сохраняется через `useMemo` и создаётся заново только при изменении
`theme` или `toggleTheme`.

Стабильный Context value предотвращает уведомление consumers о ложном изменении
Context, но не гарантирует полного отсутствия их рендеров: компонент всё ещё
может рендериться из-за родителя, props, собственного state или другого Context.
На маленьком Todo практическая экономия несущественна; hooks применены как
учебный пример ссылочного равенства, а не как шаблон для каждой функции.

## 38. Семантический HTML и доступные имена — текущий урок

Семантический элемент сообщает браузеру назначение содержимого и даёт готовое
поведение клавиатуры и accessibility tree. Выбор начинается со смысла, а не с
внешнего вида: действие — `button`, поле — `input` с `label`, основной контент —
`main`, список однотипных записей — `ul/li`, пары термин/значение — `dl/dt/dd`.

Form-control должен иметь доступное имя — текст, который вспомогательная
технология связывает с элементом. Placeholder не заменяет label, а просто
стоящий рядом текст не создаёт связь. Нативный `label` связывается через
`htmlFor`/`id` либо оборачиванием control и текста; клик по label тогда также
активирует control.

Предпочтителен нативный HTML, а ARIA добавляется только там, где HTML не выражает
нужное состояние или имя. Нельзя вкладывать посторонние интерактивные элементы в
label checkbox: кнопки удаления, дублирования и приоритета должны оставаться
снаружи, иначе их взаимодействие может затронуть checkbox.

Первый аудит Todo: структура страницы, формы, списка и статистики в целом
семантична. Checkbox задачи пока не имеет доступного имени. Практика — объединить
его с видимым `TodoContent` оборачивающим label и сохранить flex-раскладку
отдельным классом этой группы.

Практика label выполнена: checkbox и видимый текст находятся внутри одного
`label`, поэтому название стало доступным именем, а область клика расширилась.
Action-кнопки не вложены в label. CSS-контейнер группы с `flex: 1` и
`min-width: 0` сохраняет место для действий и позволяет тексту сжиматься.

`section` используется для самостоятельной смысловой части документа и обычно
имеет заголовок. После единственного `h1` страницы следующий уровень для раздела
списка — `h2`. `aria-labelledby` может явно связать section с `id` этого
видимого заголовка; придумывать отдельный невидимый `aria-label` тогда не нужно.

Практика структуры выполнена: поиск и список входят в именованный `section`
«Задачи», а заголовки образуют уровни `h1 → h2`. Семантические элементы, формы,
labels и явные типы кнопок закреплены на текущем интерфейсе.

## 39. Клавиатура и видимый focus — пройдено

Нативные `button`, `input` и checkbox уже поддерживают клавиатуру: Tab и
Shift+Tab перемещают focus, Enter отправляет форму или активирует подходящую
кнопку, Space активирует кнопку и переключает checkbox. Замена их кликабельным
`div` потребовала бы вручную восстанавливать роль, focus и клавиши.

Пользователь клавиатуры должен видеть текущий сфокусированный элемент. Нельзя
удалять outline без равноценной замены. Псевдокласс `:focus-visible` обычно
показывает авторский focus-ring при клавиатурной навигации, не навязывая его при
обычном клике мышью. `outline` не меняет размеры элемента, а `outline-offset`
создаёт расстояние от его границы.

Практика выполнена: интерактивные элементы внутри layout получили тематическое
кольцо `:focus-visible`, при этом нативный порядок focus и клавиатурное поведение
не переопределялись.

## 40. Каскад, специфичность, наследование и box model — пройдено

Запись `.todo-layout input:focus-visible` целиком называется CSS-селектором и
состоит из нескольких частей:

- `.todo-layout` — селектор класса;
- пробел — комбинатор потомка: искать внутри элемента с этим классом;
- `input` — селектор типа HTML-элемента;
- `:focus-visible` — псевдокласс.

Псевдокласс начинается с одного двоеточия и выбирает элемент в определённом
состоянии или положении, не добавляя новый класс в HTML. Примеры состояний:
`:hover`, `:focus`, `:checked`, `:disabled`; пример положения — `:first-child`.
`:focus` срабатывает при любом получении фокуса, а `:focus-visible` — когда
браузер считает, что пользователю нужен видимый индикатор фокуса, прежде всего
при клавиатурной навигации.

Псевдокласс отличается от псевдоэлемента. Псевдоэлемент обычно записывается с
двумя двоеточиями и выбирает условную часть элемента: `::before`, `::after`,
`::placeholder`. Иными словами, `:hover` описывает состояние настоящего
элемента, а `::before` — создаваемую CSS условную часть этого элемента.

CSS-правило не заменяет другое правило целиком. Браузер выбирает значение
отдельно для каждого свойства. Поэтому два блока `.todo-actions` с одинаковым
селектором фактически объединяются: неповторяющееся `flex: 0 0 auto` из первого
остаётся, а при конфликте одинаковых свойств победит более поздняя запись.

Упрощённый порядок выбора значения: сначала важность и источник стиля, затем
специфичность селектора, а при равенстве — правило, записанное позже. Селектор
элемента (`button`) слабее класса (`.todo-actions`), класс слабее сочетания
класса и элемента (`.todo-actions button`). `!important` не является обычным
способом исправлять непонятый каскад.

Наследование — другой механизм: некоторые свойства, например `color` и
CSS-переменные, переходят от родителя к потомкам. `display`, `margin`, `border`
и `background` обычно не наследуются. Наследование не означает, что дочерний
элемент автоматически получает все CSS-свойства родителя.

Свойство также должно быть применимо к элементу в его текущем режиме раскладки.
Например, `flex-direction` управляет только flex-контейнером. У обычной кнопки
без `display: flex` эта запись ничего не меняет, хотя DevTools показывает её как
валидное объявление.

Первый проектный шаг выполнен: повторяющиеся правила `.todo-actions` объединены,
а неприменимое `flex-direction` удалено. Это только первая практика урока;
специфичность, порядок записи и наследование продолжают разбираться отдельно.

Специфичность закреплена на конфликте `button` и `.todo-actions button`: второй
селектор сильнее, потому что кроме элемента содержит класс. Если два селектора
полностью одинаковы, при прочих равных побеждает объявление, записанное ниже.
В DevTools проигравшее значение отображается перечёркнутым.

Наследование отличается от каскада: потомок может получить вычисленное значение
родителя, если свойство наследуется и собственное правило его не переопределило.
Обычно наследуются текстовые свойства (`color`, `font-family`, `font-size`,
`line-height`) и CSS custom properties. Размеры, `display`, `margin`, `padding`,
`border`, `background`, flex-настройки обычно не наследуются.

В Todo наследуется `--border-color`, но не сама граница: каждый `.todo-item`
явно создаёт свой `border` и только читает унаследованную переменную. Элементы
формы могут иметь собственный браузерный шрифт, поэтому для `button` и `input`
явно задано `font: inherit`. Обычный `ul` в таком правиле не нужен: он уже
наследует шрифт естественно.

### Box model

Псевдоэлемент — создаваемая CSS условная часть элемента, которой нет отдельным
узлом в JSX/HTML. `::before` располагается внутри выбранного элемента перед его
обычным содержимым, а `::after` — после содержимого. Обычно они появляются,
когда задано свойство `content`; например, пустой `content: ""` создаёт
декоративную коробку, которую можно оформить фоном, размером и позиционированием.

Запись `.todo-item::before` означает «псевдоэлемент before каждого элемента с
классом todo-item». Два двоеточия отличают псевдоэлемент от псевдокласса:
`:hover` выбирает состояние существующего элемента, а `::before` выбирает
генерируемую часть. Другие примеры: `::after`, `::placeholder`, `::marker`,
`::selection`, `::first-letter`.

Существенный текст и доступные названия не следует помещать только в `content`:
псевдоэлементы предназначены прежде всего для оформления, а важная информация
должна оставаться в HTML. Универсальный `*` выбирает реальные элементы, но не их
псевдоэлементы. Поэтому reset перечисляет `*::before` и `*::after` отдельно;
если такие декоративные коробки появятся позже, их размеры тоже будут считаться
с `box-sizing: border-box`.

Каждый отображаемый CSS-блок состоит из вложенных областей: content, затем
padding, затем border, а снаружи margin. Фон элемента рисуется под content и
padding (и по умолчанию до внешнего края border), тогда как margin остаётся
внешним прозрачным расстоянием. `outline` находится снаружи границы и не влияет
на расчёт размера или положение соседей.

При стандартном `box-sizing: content-box` заданные `width`/`max-width` относятся
к области content. Горизонтальные padding и border добавляются сверху к этому
размеру. Поэтому `max-width: 600px` и `padding: 0 16px` могут дать border-box
шириной 632px. При `box-sizing: border-box` объявленная ширина уже включает
content, padding и border; браузер уменьшает content, чтобы общий border-box не
превысил заданное значение.

Margin не входит ни в content-box, ни в border-box. В `margin: 40px auto`
вертикальные поля равны 40px, а оставшееся горизонтальное место делится между
левым и правым `auto`, поэтому ограниченный по ширине layout центрируется.

Практика завершена общим reset `box-sizing: border-box` для элементов и
`::before`/`::after`. При общей ширине 600px, горизонтальных padding по 16px и
границах по 2px content получает `600 - 32 - 4 = 564px`. При `content-box` те же
padding и границы добавились бы снаружи ширины content.

## 41. Flexbox — пройдено

`display: flex` делает выбранный элемент flex-контейнером. Только его прямые
дочерние элементы становятся flex-элементами; более глубокие потомки не входят
в эту раскладку автоматически. Один элемент может одновременно быть flex-item
своего родителя и flex-container для собственных детей.

У контейнера две оси. Главная ось задаётся `flex-direction`: при `row` она идёт
слева направо, при `column` — сверху вниз. Поперечная ось всегда перпендикулярна.
`justify-content` распределяет элементы вдоль главной оси, `align-items` — вдоль
поперечной. Поэтому смысл этих свойств меняется при смене `flex-direction`.

`gap` создаёт расстояние только между соседними flex-items и не добавляет отступ
между крайними элементами и границей контейнера; за внутренние края отвечает
`padding`. `flex-wrap` определяет, остаются ли элементы на одной линии или могут
переноситься при нехватке места.

Свойства контейнера (`display`, `flex-direction`, `justify-content`,
`align-items`, `gap`, `flex-wrap`) управляют группой прямых детей. Свойства item
(`flex`, `flex-grow`, `flex-shrink`, `flex-basis`, `align-self`, `order`) задаются
самому ребёнку и определяют его поведение внутри родительского flex-контейнера.

Сокращение `flex` объединяет grow, shrink и basis. Практически `flex: 1`
означает, что элемент может занять свободное место и делить его с другими
растягиваемыми items; `flex: 0 0 auto` запрещает рост и сжатие, оставляя базовый
размер по содержимому. У текстового flex-item часто требуется `min-width: 0`,
потому что автоматический минимальный размер иначе может запрещать ему сжиматься.

В текущем проекте `.todo-layout` — column-контейнер, а его прямые компоненты —
items. `.todo-item` — row-контейнер; `.todo-toggle` растягивается через `flex: 1`,
а `.todo-actions` сохраняет размер по содержимому. Один `.todo-toggle` при этом
сам является flex-контейнером для checkbox и текста.

Первая практика выполнена на форме. `.todo-form` — контейнер, а `label`, `input`
и `button` — его прямые items. Input получает оставшееся место через `flex: 1`
и может стать уже содержимого благодаря `min-width: 0`. Кнопка с
`flex: 0 0 auto` не растёт, не сжимается и берёт базовый размер по содержимому;
одного `flex-grow: 0` для полного описания этого поведения недостаточно.

Вторая практика выполнена во вложенном layout header. `.todo-header-actions`
является flex-item column-контейнера `.todo-header` и одновременно собственным
row-контейнером для трёх кнопок. `flex-wrap: wrap` разрешает перенос при узком
окне, `gap` разделяет элементы и линии, а `align-items: center` выравнивает items
по поперечной оси. Для layout-группы выбран нейтральный `div`, status оставлен
отдельным элементом.

## 42. CSS Grid — пройдено

Grid строит раскладку по строкам и колонкам одновременно, тогда как Flexbox в
первую очередь распределяет элементы вдоль одной главной оси. Это не конкуренты:
Grid удобен для внешней сетки областей, а Flexbox — для содержимого одной строки
или колонки. Один grid-item может оставаться flex-контейнером для своих детей.

`display: grid` делает элемент grid-контейнером, а только его прямых детей —
grid-items. `grid-template-columns` описывает размеры колонок, а
`grid-template-rows` — строк. Промежуток между tracks задаётся знакомым `gap`.
Если items явно не размещены, auto-placement последовательно раскладывает их по
созданной сетке.

Колонки и строки называются tracks, а границы между ними — grid lines. Две
колонки образуют три вертикальные линии. Items можно размещать по номерам линий,
именованным областям или оставить автоматическую раскладку.

Единица `fr` получает долю свободного места после размеров `auto`, фиксированных
треков и промежутков. В `1fr auto` вторая колонка берёт размер содержимого, а
первая — остаток. Однако обычный `1fr` имеет автоматический минимальный размер,
связанный с содержимым; длинный текст может вызвать переполнение.
`minmax(0, 1fr)` разрешает первой колонке сжиматься до нуля и затем получать одну
долю остатка — grid-аналог важной идеи `min-width: 0` во Flexbox.

`fr` сокращается от fraction — «доля» — и является специальной гибкой единицей
размера grid-track. Сначала из доступной ширины вычитаются фиксированные tracks,
размеры содержимого и gaps, затем остаток делится пропорционально числам перед
`fr`. В `1fr 2fr` всего три доли: первая колонка получает 1/3 остатка, вторая —
2/3. Один `1fr` получает весь остаток. Это не процент от полной ширины и `fr`
нельзя использовать как обычный `width`; он предназначен для размеров tracks в
Grid, в том числе как максимальная граница `minmax()`.

В `.todo-item` есть два прямых ребёнка: `.todo-toggle` и `.todo-actions`.
Внешняя сетка может дать первому `minmax(0, 1fr)`, а второму `auto`. При этом оба
ребёнка сохраняют собственный `display: flex` для checkbox/текста и кнопок.
Старые `flex` у самих этих двух элементов перестают описывать внешнюю раскладку,
потому что их родитель больше не flex-контейнер.

Практика выполнена на `.todo-item`. Внешний Grid управляет двумя прямыми детьми,
а каждый из них остаётся flex-контейнером для своего содержимого. Лишняя запятая
между tracks делала всё значение `grid-template-columns` невалидным, поэтому
auto-placement создавал строки; после записи `minmax(0, 1fr) auto` элементы
занимают две колонки. `auto` получает размер группы кнопок, а единственный `1fr`
получает весь оставшийся размер.

## 43. Адаптивная вёрстка и media queries — пройдено

Viewport — видимая область страницы в CSS-пикселях. На мобильном устройстве
`<meta name="viewport" content="width=device-width, initial-scale=1.0">` сообщает
браузеру использовать ширину экрана как ширину layout viewport; в Vite-шаблоне
проекта этот meta-тег уже присутствует.

Адаптивный интерфейс меняет размеры и раскладку в зависимости от доступного
пространства. Breakpoint выбирают в точке, где конкретное содержимое перестаёт
помещаться или читаться, а не по модели телефона. Между breakpoint значения
желательно оставлять гибкими через `max-width`, `fr`, `auto`, проценты и
переносы, а не создавать отдельный макет под каждую ширину.

Media query — условный CSS-блок, а не селектор. `@media (min-width: 560px)`
применяет вложенные правила, когда viewport не уже 560 CSS-пикселей.
`max-width` действует в обратную сторону. Внутри участвует обычный каскад:
условие решает, доступно ли правило, а затем сравниваются специфичность и порядок.

Mobile-first означает, что базовые правила рассчитаны на узкое окно, а
`min-width` постепенно добавляет раскладку для более широкого. Для Todo базовая
grid-строка может иметь одну колонку, а начиная с 560px — две колонки
`minmax(0, 1fr) auto`. JSX и React-логика при этом не меняются.

Практика завершена: узкая `.todo-item` использует одну сжимаемую колонку, кнопки
могут переноситься, а `@media (min-width: 560px)` возвращает две колонки.
Media query получает текущие media features от браузера и автоматически
переоценивается при изменении viewport. Meta viewport только настраивает сам
layout viewport на мобильном устройстве; React для CSS-перестройки не нужен.

## 44. Состояния интерфейса — пройдено

Псевдоклассы позволяют выбирать существующий элемент по состоянию. `:hover`
означает наведение указателя, `:active` — момент активации, `:focus` — любой
фокус, `:focus-visible` — фокус, для которого браузер считает нужным показать
индикатор, а `:disabled` — нативно отключённый form-control.

Состояния не взаимоисключающие: disabled-кнопка может находиться под указателем,
а сфокусированная кнопка — одновременно быть hover. Поэтому каскад и селекторы
должны явно выражать приоритет. Функциональный псевдокласс `:not(:disabled)`
выбирает элемент, который не соответствует `:disabled`, и не позволяет hover-
оформлению создавать ложное впечатление активности выключенной кнопки.

JSX `disabled={condition}` при true создаёт настоящий HTML-атрибут `disabled`.
Браузер сам запрещает активацию, исключает обычную disabled-кнопку из Tab-порядка
и даёт CSS состояние `:disabled`. `aria-disabled="true"` только сообщает
состояние вспомогательным технологиям и само не блокирует click; для нативной
кнопки предпочтителен `disabled`.

Hover нельзя считать единственным способом передать смысл: у клавиатуры его нет,
а touch-устройства могут не иметь нормального наведения. Media feature
`@media (hover: hover)` позволяет применять hover-эффект только там, где основной
указатель действительно умеет наводиться. Существующий `:focus-visible` должен
оставаться независимым и заметным.

Практика button states выполнена через переменные светлой/тёмной темы. Базовый
стиль применяется ко всем кнопкам layout, hover — только к доступным кнопкам на
устройствах с hover, disabled — к нативно отключённым controls. `opacity` и
`cursor` меняют только представление и сами не блокируют событие.

Ошибка async-операции не создаёт универсальный CSS-псевдокласс: браузер не знает
смысл React reducer-state. Приложение должно выразить состояние в DOM через
условный класс/атрибут и подходящую семантику. `role="status"` сообщает обычное
обновление вежливо, а `role="alert"` предназначен для срочной ошибки и обычно
объявляется сразу. Вычисляемый `isSaveError` не требует отдельного state: он
получается сравнением существующего `saveState.status` с error-статусом.

Практика error-state завершена: reducer остаётся единственным источником статуса,
вычисляемый boolean управляет классом и ролью условно создаваемого сообщения.
Цвет дополняет текст и semantics. Учебный fake-сервис намеренно может случайно
отклонить Promise для ручной проверки ошибки; `return` после `reject` прекращает
callback и делает control flow однозначным.

## 45. SCSS — текущий урок

Sass расшифровывается как **Syntactically Awesome Style Sheets** — «синтаксически
прекрасные таблицы стилей». Это название языка и экосистемы препроцессора.
SCSS расшифровывается как **Sassy CSS** — CSS-синтаксис языка Sass. CSS, в свою
очередь, означает **Cascading Style Sheets** — «каскадные таблицы стилей».

У Sass существуют два основных синтаксиса: исходный отступный синтаксис в файлах
`.sass` и CSS-подобный SCSS в файлах `.scss`. Оба предоставляет один Sass и оба
компилируются в обычный CSS; отличаются главным образом записью. Название Sass
поэтому используется и для всей технологии, и иногда специально для отступного
`.sass`-синтаксиса, что может путать.

Sass — препроцессор стилей, а SCSS — его CSS-подобный синтаксис. Браузер не
исполняет исходный `.scss`: Vite передаёт его Sass-компилятору, получает обычный
CSS и только этот результат включает в bundle. Поэтому `sass` является
devDependency — он нужен при разработке/сборке, но не выполняется как библиотека
в браузере.

Любой обычный CSS является допустимым SCSS, поэтому stylesheet можно сначала
переименовать без переписывания. Импорт `.scss` из `main.jsx` сообщает Vite,
что этот файл должен пройти preprocessing. Установка пакета обновляет
`package.json` и `package-lock.json`; `node_modules` в commit не добавляется.

SCSS разрешает вкладывать селекторы. Внутри `.todo-layout` запись `button`
компилируется в `.todo-layout button`. Символ `&` обозначает полный текущий
родительский селектор: `&[data-theme="dark"]` становится
`.todo-layout[data-theme="dark"]`, а `&:hover` добавляет состояние тому же
элементу. Без `&` создаётся селектор потомка с пробелом, то есть другой смысл.

Вложенность не создаёт изоляцию и не отменяет каскад: браузер получает обычные
селекторы с их реальной специфичностью. Глубокая вложенность делает селекторы
сильными и связанными со структурой DOM, поэтому её ограничивают одним-двумя
осмысленными уровнями.

Sass-переменная `$name` существует только при сборке и подставляется в CSS.
CSS custom property `--name` остаётся в браузере, наследуется и может меняться
по `data-theme`. Поэтому текущие theme-переменные не следует механически
заменять на Sass variables.

Первый этап выполнен: пакет Sass установлен как build-time devDependency,
stylesheet переименован в `.scss`, а Vite собирает обычный CSS. Вложенность
закреплена на различии потомка (`button`) и того же элемента с модификатором
(`&[data-theme]`, `&.completed`). Без `&` вложенный атрибутный селектор стал бы
потомком с пробелом; с `&` атрибут относится к самому `.todo-layout`.

### Sass variables

Sass variable объявляется как `$name: value;` и существует в исходниках во
время компиляции. Компилятор подставляет значение в места использования, поэтому
в итоговом CSS имени `$name` уже нет. Такая переменная подходит для статических
design tokens сборки: spacing, одинаковых размеров, параметров mixin.

CSS custom property объявляется как `--name: value` и остаётся в итоговом CSS.
Браузер вычисляет `var(--name)` с учётом каскада, наследования и текущего DOM.
Поэтому она подходит для runtime-темы. Sass variable не может сама измениться от
`data-theme` без генерации дополнительных CSS-правил.

### Mixins

Mixin — именованный переиспользуемый блок Sass-деклараций. `@mixin name { ... }`
только определяет его и сам CSS не выводит. `@include name;` вставляет декларации
в текущий selector в этой точке выходного CSS. Параметры записываются в круглых
скобках как Sass variables; им можно дать значения по умолчанию.

`@mixin` и `@include` являются Sass at-rules — командами, начинающимися с `@`,
подобно CSS at-rule `@media`, но исчезающими после компиляции. Mixin полезен,
когда одна связная группа деклараций нужна в разных местах или с параметрами.
Если два соседних селектора имеют полностью одинаковый стиль, обычный список
селекторов через запятую часто проще; mixin не следует создавать для каждой
одиночной декларации.

Аргументы mixin можно передавать по позиции или по имени. В вызове
`@include focus-ring(2px)` значение попадает в первый параметр — `$color`, а не
в `$offset`. Запись `@include focus-ring($offset: 2px)` явно выбирает параметр и
оставляет цвет равным значению по умолчанию. Именованные аргументы особенно
полезны, когда нужно пропустить предыдущий необязательный параметр.

Практика принята: `$space-small` компилируется в обычные значения CSS, а mixin
создаёт одинаковые `outline` и `outline-offset` для кнопок и полей. В итоговом
CSS остаётся `var(--focus-color)`, поэтому цвет продолжает зависеть от активной
темы во время работы приложения. Наследование CSS custom properties помогает
передать значение потомкам, но ключевое отличие от Sass variable — сохранение в
браузере и возможность изменения через каскад и `data-theme` без новой сборки.

### Sass partials и modules

Partial — «частичный файл»: часть stylesheet, предназначенная для подключения в
другой Sass-файл. Имя начинается с `_`, например `_tokens.scss`. Такой файл не
служит самостоятельной точкой входа; основной `index.scss` собирает его через
Sass module system. При подключении подчёркивание и расширение опускаются.

Module — «модуль»: отдельный Sass-файл со своей областью имён. Команда
`@use "./styles/tokens";` загружает module один раз и создаёт namespace по имени
файла. Поэтому `$space-small` из `_tokens.scss` используется как
`tokens.$space-small`. Mixin из `_mixins.scss` вызывается через
`@include mixins.focus-ring(...)`. Namespace явно показывает происхождение
значения и предотвращает случайные совпадения имён.

`@use` нужно записывать до обычных CSS-правил. Это не то же самое, что CSS
`@import`: зависимости объединяет Sass во время сборки, а браузер получает уже
готовый CSS. Старый Sass `@import` считается устаревшим для модульной организации,
поскольку складывал имена разных файлов в общую глобальную область.

JavaScript продолжает импортировать только `index.scss`. Файлы partial не нужно
импортировать в `main.jsx`: их находит Sass по цепочке `index.scss → @use →
partial`, а Vite получает один собранный stylesheet.

Практика принята: `_tokens.scss` хранит статический `$space-small`,
`_mixins.scss` — `focus-ring`, а `index.scss` подключает их через `@use`.
Обращения `tokens.$space-small` и `mixins.focus-ring` сохраняют области имён.
Важно точное соглашение об именах: один `_` обозначает partial, а путь в `@use`
не содержит этого подчёркивания и расширения `.scss`.

## 46. Styled Components и CSS-in-JS

CSS-in-JS означает **CSS in JavaScript** — «CSS внутри JavaScript». Это название
подхода, а Styled Components — конкретная библиотека, реализующая этот подход.
Она создаёт React-компоненты со связанными стилями и во время работы приложения
добавляет сгенерированные CSS-правила и классы на страницу.

Выражение `styled.button` является фабрикой styled-компонента, а следующие за
ним обратные кавычки — tagged template literal, «тегированный шаблонный
литерал» JavaScript. Результат сохраняют в переменную с заглавной буквы, потому
что это React-компонент. При рендере он создаёт обычный HTML `<button>`, передаёт
ему стандартные props (`type`, `disabled`, `onClick`) и добавляет generated
class для стилей.

Styled-компонент следует объявлять вне функции React-компонента. Иначе при каждом
рендере создаётся новый тип компонента, что даёт лишнюю работу и может сбрасывать
внутреннее состояние его поддерева.

Внутри шаблона остаётся обычный CSS, включая pseudo-classes и media queries.
Интерполяция `${...}` может содержать функцию: библиотека вызывает её с props и
вставляет результат в CSS. Пользовательские styling props принято начинать с
`$`; такие transient props («временные props») доступны стилям, но не передаются
как неизвестные HTML-атрибуты в DOM.

Styled Components является runtime dependency: компоненты используют библиотеку
в браузере, поэтому пакет устанавливается обычной командой без `--save-dev`.
SCSS, напротив, компилируется при сборке и не выполняется в браузере.

Первый styled-компонент принят: `PriorityButton` объявлен вне `TodoItem`, рендерит
обычный `<button>` и получает boolean transient prop из вложенного
`item.details.priority`. Само имя аргумента callback не извлекает prop: запись
`props => ...` получает весь объект, а `({ $important }) => ...` деструктурирует
из него конкретное поле.

Styled Components не отменяет обычный каскад. В практике generated class с
`font-weight` проигрывал более специфичному `.todo-layout button`, где shorthand
`font: inherit` одновременно задавал и `font-weight`. После замены shorthand на
нужные longhand-свойства `font-family` и `font-size` динамическая жирность начала
работать. Успешная сборка не обнаруживает подобные визуальные конфликты CSS.

### ThemeProvider

`ThemeProvider` — Provider библиотеки Styled Components. Он использует React
Context внутри библиотеки и передаёт вложенным styled-компонентам объект из prop
`theme`. Интерполяционная функция затем получает этот объект как `props.theme`.
Provider не создаёт тему, не хранит state и не переключает значения сам: при
изменении переданного объекта React обновляет потребителей.

Существующий пользовательский `ThemeContext` и библиотечный `ThemeProvider`
решают разные задачи. Первый предоставляет обычным компонентам имя темы и
`toggleTheme`; второй предоставляет styling tokens styled-компонентам. При этом
источник истины остаётся один — строковый `theme` state в `App`. Светлый или
тёмный объект выбирается как производное значение, а не хранится во втором state.

Theme object — обычный JavaScript-объект со значениями дизайна: цветами,
интервалами или размерами. Такие объекты объявляют вне компонента, чтобы не
создавать новую ссылку на каждом рендере. `ThemeProvider` должен быть предком
styled-компонента, которому требуется `props.theme`.

Практическое подключение `ThemeProvider` к Todo осознанно пропущено после разбора
механизма. Зафиксировано понимание: существующий state выбирает один из
статических theme objects, Provider передаёт его потомкам, а styled-компонент
читает значения через `props.theme`; отдельный state для объекта не нужен.

## 47. SCSS, CSS Modules и CSS-in-JS

Эти названия отвечают на разные вопросы. SCSS определяет удобный исходный
синтаксис и компилируется в CSS, но сам по себе не делает классы локальными.
CSS Modules преобразует локальные имена классов при сборке и возвращает в
JavaScript объект соответствий. CSS-in-JS связывает стили с JavaScript-компонентом;
в случае Styled Components правила создаёт runtime-библиотека.

CSS Module распознаётся Vite по имени `*.module.css`; вариант `*.module.scss`
одновременно использует Sass и модульную локализацию. Например, исходный класс
`.title` получает уникальное собранное имя, а default import `styles` содержит
`styles.title` с этой строкой. Это не Shadow DOM: в браузере остаётся обычный
класс и обычный каскад, но случайное совпадение исходных локальных имён между
разными module-файлами исключается.

CSS Modules работает при сборке и не требует runtime-библиотеки. Динамику обычно
выражают выбором одного или нескольких классов в `className` либо CSS custom
properties. Styled Components удобен, когда стиль тесно связан с props/theme,
но добавляет JavaScript-зависимость и не отменяет специфичность. SCSS удобен для
общих tokens, mixins, reset и крупных таблиц стилей, однако глобальные селекторы
нужно дисциплинированно именовать.

Выбор не обязан быть единственным на весь проект: глобальный SCSS может задавать
reset и CSS custom properties, CSS Modules — локальные стили компонентов, а
Styled Components — отдельные динамические элементы дизайн-системы. Важнее
единые правила команды, чем механическое использование всех подходов сразу.

Практика принята: `TodoContent.module.scss` экспортирует mapping для локальных
классов `content` и `completed`, а JSX всегда добавляет базовый класс и условно
добавляет модификатор. Суффикс должен быть ровно `.module.scss`: вариант
`.modules.scss` Vite воспринимает как обычный stylesheet и не создаёт default
export. CSS Module проверен не только сборкой, но и computed style в браузере.

## 48. HTTP, JSON и локальный API

HTTP — **HyperText Transfer Protocol**, «протокол передачи гипертекста».
Клиент отправляет request, server возвращает response. Request содержит method,
URL, headers и иногда body; response — status code, headers и обычно body.

URL — **Uniform Resource Locator**, «унифицированный указатель ресурса». В
`http://localhost:3001/todos` находятся scheme `http`, host `localhost`,
port `3001` и path `/todos`. Vite и JSON Server работают отдельными
процессами на разных портах.

JSON — **JavaScript Object Notation**, текстовый формат обмена данными, а не
JavaScript-объект. `JSON.stringify` сериализует значение в строку,
`response.json()` асинхронно читает body и разбирает JSON обратно.

Коды 2xx обозначают успех, 4xx — запрос клиента нельзя выполнить, 5xx — ошибку
server. Ответ 404/500 всё ещё является HTTP-response; network error означает,
что нормальный response получить не удалось.

JSON Server читает `db.json` и предоставляет коллекцию `todos` как локальный
REST API. Это учебный backend, но запросы, status, headers и сохранение изменений
в файле настоящие.

## 49. `fetch`, REST и CRUD

`fetch(url, options)` возвращает Promise объекта `Response`. Без options
используется GET. Для JSON-мутаций options содержит стандартные поля `method`,
`headers` и `body`:

```js
const response = await fetch("/example", {
  method: "POST",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify(value)
})
```

`fetch` обычно не отклоняет Promise из-за HTTP 404/500, поэтому после ответа
обязательно проверяется `response.ok`. JSON-body читается только после этой
проверки. У DELETE body часто пустое, поэтому безусловный `response.json()`
может быть ошибкой.

CRUD — **Create, Read, Update, Delete**: создание, чтение, обновление и удаление.
Для текущего ресурса используются:

- `GET /todos` — список;
- `POST /todos` — создание;
- `PATCH /todos/:id` — частичное изменение;
- `DELETE /todos/:id` — удаление.

В проекте транспорт вынесен в `todoApi.js`. Компонент или custom hook решает,
когда вызвать API и как обновить React-state. После POST/PATCH в state кладётся
server-response, потому что server может добавить id или нормализовать данные.
Сейчас используется пессимистичная модель: UI меняется после успешного ответа.

## 50. Состояния server request

Данные и состояние запроса — разные значения. Reducer моделирует `idle`,
`loading`, `success` и `error`. Empty — не ошибка, а успешный ответ с пустым
массивом. Спокойное сообщение может иметь `role="status"`, ошибка —
`role="alert"`.

Один глобальный status подходит только для одного последовательного запроса.
Если запросы A и B идут параллельно, success A не означает, что B завершён.
Для мутаций обычно нужны pending-состояния по операции или id ресурса либо общий
счётчик активных запросов.

## 51. `AbortController` и гонки — в процессе

`AbortController` создаётся для конкретного запроса. Его `signal` передаётся
в options `fetch`, а cleanup Effect вызывает `abort()`. Intentional
`AbortError` не должен отображаться как server/network error.

В development Strict Mode проверяет Effect циклом setup → cleanup → setup.
Cleanup отменяет первый GET, второй остаётся актуальным. API-клиент не должен
знать о React lifecycle: controller принадлежит Effect или custom hook, а
`todoApi` лишь принимает optional signal.

Abort уменьшает лишнюю работу, но не гарантирует порядок всех результатов.
Политика latest-wins дополнительно сравнивает request id перед изменением state.
Для POST/PATCH/DELETE abort не гарантирует откат на server: запрос мог уже
изменить данные. Конфликтующие мутации нужно блокировать, ставить в очередь либо
обрабатывать через optimistic update и rollback.

Текущая реализация умеет отменять первоначальный GET, но защита гонок не принята:
request id не координирует мутации, а один `apiState` не описывает несколько
параллельных операций.

## Частые ошибки, которые уже встречались

- Запуск npm не в каталоге с `package.json`.
- Попытка прочитать специальный `key` внутри props.
- Передача результата вызова вместо функции в обработчик.
- Использование `value` вместо `checked` у checkbox.
- Дублирование `completed` в локальном state.
- Мутация текущего массива и возврат той же ссылки из setter.
- CSS-класс написан в JSX через точку вместо пробела.
- Путаница между `.a.b` (один элемент с двумя классами) и `.a .b` (потомок).
- Неявный `type="submit"` у кнопки.
- Вывод чисел без понятных текстовых подписей.
